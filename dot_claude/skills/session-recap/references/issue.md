# issue: Issue のコメント

仕事の Issue に、作業の状況を関係者向けにコメントする形。読み手は、同じチームの開発者や、仕様を決める人、作業を引き継ぐ人。読み手が知りたいのは、何が終わり、何が確かめられ、何が残っていて、自分が何をすればよいかだ。

## 構成

```markdown
## <日付> の対応状況

<1〜2 文で、今どこまで進んだか>

### 対応したこと
- <変えたこと。1 項目 1〜2 文。関連するコミットや PR を添える>

### 確認したこと
- <動作の確認、テストの結果、再現の手順。確かめた環境も書く>

### 残っていること
- <未対応、未確認のこと>

### ご相談・お願い
- <判断してほしいこと、レビューの依頼。誰に向けたかが分かるように>
```

当てはまる中身のない節は、見出しごと省く。

## 書き方

- 敬体（です・ます）。
- Claude との作業の過程（使ったスキル、道具の回数、Claude とのやり取り）は書かない。読み手が知りたいのは、作業の結果と判断の理由だからだ。ユーザーが過程も共有したいと言ったときだけ書く。
- コミットは短いハッシュで書き、リモートが分かれば（`git remote get-url origin`）リンクにする。PR は URL で書く。
- 判断を書くときは、根拠になった事実（測った値、確かめた結果）も 1 文で添える。
- 社外秘の値（本番の URL、顧客名、認証情報）は書かない。Issue の公開範囲が分からなければ、ユーザーに確かめる。
