# session-recap

セッションの記録から事実を抜き出し、用途に合う形の文章にする。記録には、ユーザーの依頼、Claude が呼んだ道具、`/` で打ったスキル、書き換えたファイルが時刻つきで残っている。会話の記憶より正確なので、まず記録から事実を集め、そのあとで書く。

## 1. 形を決める

| 形 | 用途 | 書き方 | 推敲 |
|---|---|---|---|
| `devlog` | 開発日誌。Obsidian などに貼る。公開もありうる | `references/devlog.md` | yomiyasu（技術記事） |
| `summary` | 自分が中身をつかむだけ | `references/summary.md` | しない |
| `issue` | 仕事で関係者に共有する Issue のコメント | `references/issue.md` | yomiyasu |

依頼の言葉から選ぶ。「日誌」「振り返りを残したい」なら devlog、「何をしたか教えて」「ざっと知りたい」なら summary、「Issue に」「チームに共有」なら issue。決めきれないときだけ、1 回だけ尋ねる。

範囲は、指定がなければ「今日、今の作業フォルダで行ったセッションすべて」にする。日付、セッション、昔の作業フォルダの名前を言われたら、それに合わせる。

## 2. 事実を集める

`scripts/session_digest.py` を実行する。標準ライブラリだけで動く。

```bash
python3 <このスキルのフォルダ>/scripts/session_digest.py \
  [--date YYYY-MM-DD] [--project 作業フォルダ ...] [--session セッションIDの頭 ...] [--tz Asia/Tokyo]
```

出力は Markdown で、セッションごとの時間、道具の回数、ユーザーが `/` で打ったコマンド、Claude が `Skill` で呼んだスキル、サブエージェント、書き換えたファイル、依頼の流れ（時刻つき）と、その日のコミットが並ぶ。

- 作業フォルダの探し方: 記録の中の `cwd` で探す。作業フォルダの名前を途中で変えたプロジェクトは、古いパスも `--project` で重ねて渡す。候補は `ls ~/.claude/projects` で、似た名前のフォルダを探すと見つかる。
- フォークしたセッション: 元の記録を複製しているので、スクリプトは同じ記録を 2 回数えない。フォークの側には、分かれたあとに増えた分だけが残る。
- アプリの道具: デスクトップアプリのタスク一覧の道具（`mcp__ccd_turn__*`）は、作業の中身ではないので数えない。
- 足りないとき: Claude の返答の中身や、ある時刻の前後の様子が必要なら、該当するセッションの jsonl を jq で読む。たとえば、時刻を絞って Claude の文章だけを読むには次のようにする。

```bash
jq -r 'select(.type=="assistant" and .timestamp >= "2026-10-18T05:00") | .message.content[]? | select(.type=="text") | .text[0:300]' <セッション>.jsonl
```

devlog で使ったスキルを説明するときは、そのスキルの SKILL.md も読み、「説明書が求めること」と「実際に起きたこと」を突き合わせる。置き場所は `~/.claude/skills/<名前>/`、プロジェクトの `.claude/skills/<名前>/`、プラグインなら `~/.claude/plugins/cache/` の下（`find ~/.claude/plugins/cache -path '*/<名前>/SKILL.md'`）。

今いるセッションも記録に入っているが、会話として手元にある内容のほうが詳しい。両方を突き合わせる。

## 3. 書く

選んだ形の `references/<形>.md` を読み、その構成と文体で書く。どの形でも、次の事実の守り方は同じ。

- 確かめたことだけを書く。記録、ファイル、コマンドの出力、ユーザーの発言で確かめていないことは、書かないか「と考えられる」「だろう」のように推量と分かる形にする。読めなかった資料の中身や題名を、推測で埋めない。
- 誰が動かしたかを分ける。「ユーザーが `/` で打った」「Claude が `Skill` で呼んだ」「Claude がファイルとして読んだ」は別のことなので、混ぜずに書く。スキルが「自動で動いた」と書くのは、記録に `Skill` の呼び出しがあるときだけにする。
- 数は数えたものを書く。回数、件数、時刻は、スクリプトの出力か、自分で数えた結果から写す。
- 引用は言葉どおりにする。ユーザーの依頼を「」で引くときは、言い換えない。長いなら、引用をやめて地の文で要約する。
- 途中で間違いが分かったら、その間違いも残す。前の記録の誤りを直した経緯は、読み手の学びになる。

## 4. 渡す前の確認

devlog と issue は、ほかの人が読む前提で、次を確かめる。見つけたら、消すか、一般的な言い方にする。

- 手元のパス（`/Users/<名前>/...`、iCloud や Obsidian の保管庫のパス）。作業フォルダは、プロジェクト名だけで足りる。
- メールアドレス、アクセストークン、パスワードのような値。
- ユーザーが貼り付けた文章の中身。スクリプトは貼り付けを「[貼り付け N 文字]」に縮めているが、jq で読み足した部分には残っていることがある。
- 健康や家族、職場の内情のような個人的なこと。issue では、その職場の関係者に共有する範囲の話だけを残す。

確認には、たとえば次のように grep を使う。

```bash
grep -n -E '/Users/|@[a-z0-9.-]+\.[a-z]{2,}|iCloud|Obsidian|token|password' <書いたファイル>
```

## 5. 推敲する

devlog と issue は、yomiyasu スキルがあれば、それで推敲する。原文がない新規作成なので、手順 2 の出力と、会話で確かめた事実を書き出したファイルを資料（`--material`）として渡す。devlog は種類を技術記事（`--doc-type article`）にする。issue は種類を決めずに進め、業務の文書として直す。yomiyasu がなければ推敲は省き、省いたことを伝える。

summary は推敲しない。速く中身をつかむための形なので、事実が正しければ足りる。

## 6. 渡す

- devlog と issue: 本文を返答に載せ、そのままコピーできるようにする。本文にコードの囲みが入るので、外側は 4 つのバッククォート（```` ```` ````）の囲みにする。同じ本文を作業用のフォルダにも保存する。セッションに作業用のフォルダ（scratchpad）があればそこに、なければ `~/.claude/tmp/session-recap/` に置く。プロジェクトのリポジトリには書かない。公開するかどうかはユーザーが決める。
- summary: 返答に書くだけにする。ファイルは作らない。

返答の最後に、確かめられなかったこと（推量で書いた箇所、読めなかった記録）を短く添える。
